# BHARATI · Digital Twin

**Remote Operations Console for India's Antarctic Station — Bharati**

Interactive, role-aware MVP for **SIH Problem Statement 26060: "Digital Twin
for Remote Management of India's Antarctic Stations"** — problem setter: NCPOR
(National Centre for Polar and Ocean Research, Ministry of Earth Sciences).
Scope: **Bharati station only** (Larsemann Hills, Prydz Bay).

> All telemetry in this application is **simulated**. NCPOR does not publish
> operational figures for its stations, so nothing here reflects real live
> data — every live value is generated by an in-browser simulation engine and
> is labelled as *Simulated* throughout the UI.

## The problem

India operates two year-round Antarctic research stations:

- **Maitri** — Schirmacher oasis
- **Bharati** — Larsemann Hills, on the shore of Prydz Bay; the newer of the
  two, commissioned in 2012.

Wintering over in Antarctica means total isolation: the crew operates the
station without external support for months, and the **only** link to India is
a satellite connection (Bharati hosts an AGEOS-class ground station). Remote
management from NCPOR Hq requires:

- knowing *in real time* what is happening at each physical subsystem,
- detecting degradation **before** it becomes a failure,
- keeping the station safe when the communication link itself drops.

SIH PS 26060 asks for a **Digital Twin** — a live, interactive mirror of the
physical station that an operator at Hq or on station can interrogate as if
they were looking at the real thing. This MVP covers the **Bharati** footprint:
power generation, fuel logistics, sea-water utilities, seasonal shelter and the
satellite ground station.

---

## What the solution is

A single-page, self-contained web application (no backend, no auth) that
simulates the Bharati *living* digital twin.

The twin is **stateful and continuous**: a reducer-driven simulation engine
ticks every 2 seconds, walks every telemetry quantity along a bounded random
path, derives subsystem health from thresholds, fires alerts on band
transitions, and supports a full **offline-first (store-and-forward)**
communication story — the single most important behaviour in the product.

Three roles see three genuinely different consoles (see
[Role-based views](#role-based-views)) — this is behavioural, not cosmetic.

The app is built to be **operated by a judge**, not just watched:

- every control is clickable and has a visible, state-driven reaction
- every live value is rendered in a monospace face so digits never jitter
- every panel is flat with a 1 px hairline border — no decorative shadows
- state-change animations exist only to make changes *legible* (status colour
  transitions, the sync flush progress bar, the fuel-runway number recompute)

## Technology stack

| Layer | Choice | Why |
|-------|--------|-----|
| Framework | **Vite + React 19 + TypeScript** | fast dev server, strict typing, single deployable SPA |
| Styling | **Tailwind CSS v4** (`@tailwindcss/vite`) | design tokens via CSS `@theme`, no config drift |
| Animation | **Framer Motion** (`framer-motion`) | only for *state* micro-interactions (status colour transition, sync flush progress, runway recompute, role-tab pill, panel entry/exit) — no decorative fade-ins |
| Charts | **Recharts v3** | live sparklines with threshold reference lines; `isAnimationActive={false}` so charts update without jitter |
| Icons | **lucide-react** | minimal, tree-shakeable |
| Fonts | **@fontsource** (bundled, offline-safe) — *Space Grotesk* (UI/headings) + *IBM Plex Mono* (all live numeric readouts) | self-hosted so the app works with no network; mono face prevents digit jitter |
| AI layer | **Groq API** (`openai/gpt-oss-20b`) via a serverless-style `api/predict.ts` route | agentic forecasting of cascade effects from operator-driven overrides — see [Agentic AI layer](#agentic-ai-layer) |

The simulation itself lives entirely in the browser. The only outbound call is
`POST /api/predict`, served as Vite dev/preview middleware (the Groq key stays
on the server side and never reaches the client).

The visual language is deliberately "operated hardware", not "candy SaaS":

| Token | Value | Use |
|-------|-------|-----|
| `midnight` | `#0a1420` | app background (deep polar night) |
| `abyss` | `#050b13` | header / footer / inset wells |
| `panel` / `panel2` | `#0e1b29` / `#122237` | cards |
| `line` / `line-soft` | `#1d3348` / `#16283b` | 1 px hairline borders |
| `glacial` | `#5ec8d8` | primary data accent / nominal link |
| `ok` | `#4ade80` | "online / nominal / green" |
| `amber` | `#f5a623` | warnings |
| `crit` | `#ff5a5f` | critical |
| `ink` / `slate-mid` / `slate-dim`/`slate-faint` | `#e6f0f7` / `#9fb8cc` / `#64809a` / `#3d5a73` | text hierarchy |

Principles enforced in `src/components`:

- **Flat panels**: hairline 1 px border, minimal radius, no card shadows.
- **Two type families**: Space Grotesk for UI/headings; IBM Plex Mono reserved
  *only* for live numbers, timestamps, status chips and so on.
- **No decorative motion**: Framer Motion is used for transition *between*
  states (status colour fill, hard critical blink on the map, CAD viewfinder
  brackets on selection, alert entry/exit, layout reflow on role switch, sync
  progress).
- **Blueprint realism**: the station map renders as a CAD sheet — flat land/sea
  fills (no gradients), hatch pattern water, engineering grid overlay, drawing
  frame with edge ticks, center crosshairs, redraw corners instead of rounded
  corners, and a *sharp* opacity blink (not a soft glow) on critical modules.
- **Systems status strip**: a slim global bar under the header aggregates all
  six module statuses into one blinking `SYSTEMS: ALL NOMINAL / DEGRADED /
  CRITICAL` verdict with OK/WARN/CRIT counters.
- **No arrows appended to buttons**, no ALL-CAPS eyebrow labels over
  everything (uppercase is used sparingly for small mono "SIMULATED" data tags,
  which the brief explicitly requires).
- Status → colour mapping is centralised in `components/statusTheme.ts`
  (`STATUS_HEX`, `STATUS_LABEL`, `statusLabelShort`, tailwind class maps) and
  reused by the map, chips, charts and alerts, so a severity can never drift
  between panels.

## Getting started

```bash
git clone <repo> sih_2026_mvp
cd sih_2026_mvp

npm install

# optional — enables the live Groq AI Prognosis in the Predictive Lab
cp .env.example .env        # then paste your key from console.groq.com
npm run dev
```

Open http://localhost:5173. The core simulation needs no configuration and no
network; only the **AI Predictive Lab** requires a `GROQ_API_KEY`. Run it
without a key and the lab degrades gracefully to a clearly-labelled
*local-fallback* heuristic that mirrors the same thresholds (so the demo never
breaks for a judge who has no key).

**Key handling:** the key is read server-side only — `api/predict.ts` runs as
Vite dev/preview middleware, so the key never ships to the browser. It is
configured via `.env` (gitignored) or the `GROQ_API_KEY` shell variable.

## Simulation engine deep-dive

All simulation behaviour lives in `src/simulation/`, built on a **pure
reducer** over one central piece of state. This keeps the UI trivially
reactive (every control is just an action dispatch) and makes the whole system
unit-testable without a browser.

### State model (`types.ts` → `SimState`)

```ts
role              // 'admin' | 'leader' | 'scientist'
now / tick        // wall-clock + monotonic tick counter
satelliteOnline, syncing, syncTotal, queuedPackets
generatorFailed, recovering
temp{ v, history[], band }, gen{...}, fuel{...}   // telemetry channels
burnRate, daysRemaining
stormTicksLeft, loadSpikeTicks, seaState
modules            // Record<ModuleId, ModuleState> — derived per tick
selected           // selected map region
alerts[]           // newest-first, capped at 60
```

### Actions (`reducer.ts` → `SimAction`)

| Action | Effect |
|--------|--------|
| `TICK` | advance one simulation step (every 2 s, fired by the provider) |
| `SET_ROLE` / `SELECT` | active role / selected module |
| `ACK` | mark an alert acknowledged (HQ Admin) |
| `GEN_FAIL` / `RESET_NOMINAL` | what-if drill + recovery |
| `SAT_OFFLINE` / `SAT_ONLINE` / `SYNC_DONE` | store-and-forward lifecycle |

### The tick loop

A `TICK` computes, deterministically-in-order:

1. **Ambient temperature** — bounded random walk around a nominal surface-air
   value. An occasional **storm regime** (probability `STORM_START_P` per tick,
   7–18 ticks long) applies a `-1.25 °C/tick` bias, so the temperature
   periodically descends through `-28` (warning) and occasionally reaches
   `≤ -35` (critical). This guarantees the alert feed is observably alive
   during a short demo.
2. **Generator load** — random walk around the ~62 % operating point
   (clamped 40–86 %). An occasional **heating-load spike** regime
   (probability `LOAD_SPIKE_START_P`, 6–14 ticks) biases the walk upward so the
   `80 %` margin warning is actually crossed on-screen.
3. **Fuel / burn** — reserve decreases by `burnRate × TICK_DT_DAYS` per tick.
   Burn is `1.55 %/day` nominal and `3.2 %/day` under backup power; the runway
   (**days of fuel = reserve ÷ burn**) recomputes every tick.
4. **Sea-water intake** — `0..1` walk; `> 0.72` flags frazil-ice in the intake.
5. **Store-and-forward** — if the satellite link is down, `+8 packets` per tick
   (edge processing continues uninterrupted).
6. **Module statuses** — every module's `ok/warning/critical` is re-derived
   (see below).
7. **Threshold alerts** — each channel's *band* is compared to the previous
   band; **only on a transition** is an alert fired (temperature, load, fuel).
8. **Queue overflow / recovery** — caps alerts at 60, logs "backup power
   released" when the bus ramps back to nominal.

### How module status is derived (`moduleSnapshot`)

| Module | Status source |
|--------|---------------|
| Main Building | generator tripped → `critical`; load ≥ 90 → `critical`; ≥ 80 → `warning`; else `ok` |
| Fuel Farm / Fuel Station | reserve ≤ 15 → `critical`; ≤ 30 → `warning`; else `ok` |
| Sea-water Pump House | intake > 0.72 → `warning` (frazil ice); else `ok` |
| Summer Camp / Emergency Shelter | `ok` — standby, unoccupied (persistent) |
| AGEOS ground station | link down → `warning` ("store-and-forward active"); else `ok` |

`moduleSnapshot` is recomputed at the end of **every mutation**, so the map can
never be stale (e.g. the instant `GEN_FAIL` dispatches, Main Building is
already critical).

### Store-and-forward lifecycle

```
ONLINE ──click──▶ OFFLINE        edge keeps ticking; queuedPackets += 8/tick; banner warns
OFFLINE ─click──▶ ONLINE (queued > 0)
                    syncing=true, syncTotal=queued    ← progress bar animates 2.4 s
                    SYNC_DONE (timer)                 ← queued=0, "N packets synced to HQ"
OFFLINE ─click──▶ ONLINE (queued = 0)                 ← instant, "nothing queued"
```

The action API in `SimProvider.tsx` also owns the two timers: the 2 s `TICK`
interval and the clamped `SYNC_DONE` flush timer (`SYNC_FLUSH_MS = 2400`), so
the reducer stays pure and deterministic.

### Generator-failure lifecycle

```
GEN_FAIL ─▶ generatorFailed=true, load→≈0, main=critical, burn 1.55→3.2 %/day,
            critical alert "Generator failure — ...", runway visibly ~halved
RESET_NOMINAL ─▶ recovering=true, load ramps +4.6 %/tick to 62, burn→1.55,
            "Generator restored" alert; on reaching target → "Backup power released"
```

## Thresholds & simulation parameters

Single source of truth: `src/constants.ts`.

| Quantity | Nominal | Warning | Critical | Clamp / notes |
|----------|---------|--------:|:--------:|---------------|
| Ambient temp | −25…0 °C | ≤ −28 or ≥ 2 °C | ≤ −35 or ≥ 5 °C | −38…6 °C; step 0.4; storm bias −1.25 |
| Generator load | ~62 % | ≥ 80 % | ≥ 90 % | 40–86 %; step 1.9; spike step 2.1 |
| Fuel reserve | 88.4 % start | ≤ 30 % | ≤ 15 % | floor 2.0 %; burn 1.55 %/day (3.2 backup) |
| Sea intake | ~0.4 | > 0.72 | — | 0–1; step 0.07 |
| Runway (days) | ok | ≤ 25 d | ≤ 12 d | = reserve ÷ burn |

Tempo: `TICK_MS = 2000` (one tick ≈ 29 sim-minutes, `TICK_DT_DAYS = 0.02`);
`HISTORY_LEN = 90` samples per chart; alerts capped at 60; `PACKETS_PER_TICK
= 8`; `SYNC_FLUSH_MS = 2400`.

## Agentic AI layer

### The route — `api/predict.ts`

A single serverless-style endpoint mounted as **Vite dev + preview middleware**
(`apply: 'serve'`), so `POST /api/predict` works both in `npm run dev` and
`npm run preview` without a separate backend service.

Request body (`PredictInput`):

```json
{
  "overrides": { "ambientTemperature": -32, "generatorLoad": 92 },
  "telemetry": {
    "ambientTemperature": -18.6, "generatorLoad": 63, "fuelReserve": 88.4,
    "fuelBurnRatePercentDay": 1.55, "seaWaterIntake": 0.42, "daysRemaining": 57
  }
}
```

### Groq invocation

- Model: **`openai/gpt-oss-20b`**. The original pick `llama3-8b-8192` has been
  **decommissioned by Groq** (returns `model_decommissioned`), so the endpoint
  uses the current open-weight flagship instead — it supports `response_format:
  { type: 'json_object' }`, `temperature: 0.2`, 12 s timeout via
  `AbortController`.
- System prompt is the spec'd diagnostic contract: output *strictly* a JSON
  object with `risk_level` (`NOMINAL|WARNING|CRITICAL`),
  `predicted_cascade_effect` (10-word cascade path), 
  `estimated_time_to_failure_hours`, and `recommended_action`.
- The user message carries the overrides, the live telemetry, **and** the app's
  own operating thresholds — so the model reasons over the same physics the UI
  enforces, which is what makes an extreme override come back `CRITICAL` while
  nominal inputs come back `NOMINAL`.

### Response validation & fallback

The Groq payload is validated before use: `risk_level` must be one of the three
allowed values, numbers must be finite, strings are truncated and the ETA
clamped to 0–8760 h. Any parse/validation error (or missing key / network
failure / 12 s timeout) falls back to a deterministic **local heuristic** that
re-derives risk from the same `constants.ts` thresholds and emits correctly
scoped cascade text, ETA and command templates.

The response (`PredictResponse`) always carries a `provider` field —
`groq` (live model) or `local-fallback` (heuristic-rule-engine) — plus `model`,
`latencyMs`, `generatedAt` and an `inputs` echo. The lab renders the big
provenance row in the result banner and tags the panel header `GROQ LIVE` /
`LOCAL FALLBACK` so a judge can always tell which engine answered.

| Status code | Meaning |
|-------------|---------|
| `200` | diagnostics returned (`groq` or `local-fallback` provider) |
| `400` | malformed JSON body |
| `405` | non-POST request to `/api/predict` |

## Testing & verification

Two layers were used to verify the whole app end-to-end.

### 1. Reducer smoke tests (no browser)

Bundling `src/simulation/reducer.ts` to CJS and driving the pure reducer lets
us assert the entire simulation contract:

- bounded histories at boot; `daysRemaining = reserve ÷ burn`
- `GEN_FAIL`: flag set, Main Building → critical, burn → 3.2, runway visibly
  shrinks, critical alert logged, load ≈ 0; double-fire is a no-op
- `RESET_NOMINAL` + recovery ramps load back to 62 and restores nominal burn
- offline: alerts, `queuedPackets` accumulates `8/tick`, AGEOS → warning,
  telemetry **keeps** ticking
- `SAT_ONLINE`: `syncing=true`, `syncTotal` = queued snapshot; no queue growth
  while syncing; `SYNC_DONE` flushes to 0 and records an `ok` alert
- deterministic fuel-band crossing fires a warning alert
- ACK, role and selection actions behave

```bash
npx esbuild src/simulation/reducer.ts --bundle --platform=node \
  --format=cjs --outfile=/tmp/simtest.cjs
node /tmp/simtest.js        # → 27 passed, 0 failed
```

### 2. Headless-browser QA (full UI, production build included)

A Puppeteer script loads the app, then drives the real UI: it verifies all
seven features by clicking the actual controls (satellite toggle → queued
packets → sync flush, generator failure → backup state → reset, role switch,
map region selection) and asserts against `document.body.innerText` — with
**zero console/page errors**. A second Puppeteer pass drives the **AI
Predictive Lab** end-to-end against the live Groq route: it sets the override
sliders to extreme inputs, clicks *Execute AI diagnostics*, waits for the
prognosis banner, and asserts risk level, cascade, ETA, recommended action,
provider badge and the inputs echo all render — then confirms the Scientist
role unmounts the lab. Both passes run clean.

## Known gotchas

- **TypeScript 6 JSX parser quirk**: an inline JSX element used directly as the
  value of a JSX *attribute* (e.g. `right={ cond ? (<span/>) : undefined }` or
  `icon={<X className="..."/>}` in some multi-attribute positions) can trip a
  `TS1003`/`TS1382` parse error. The codebase's working convention is to compute
  such nodes **into a variable first** (`const trippedChip = cond ? … : undefined`
  then `right={trippedChip}`). Keep this pattern when extending.
- **Chunk-size warning** at build (`~700 kB JS`): caused by Recharts +
  Framer Motion + React 19 being eager-imported. Deliberate for an MVP — a
  route-level dynamic import would also split it. It is a warning, not an error.
- **StrictMode double-invoke**: the dev build mounts effects twice; the two
  timers (TICK + sync flush) are written to be idempotent against that
  (`setInterval` is cleaned up; `SYNC_DONE` is a guard no-op when not syncing).
- **Groq model deprecation**: `llama3-8b-8192` has been decommissioned on Groq
  and now hard-fails with `model_decommissioned`. The endpoint therefore uses
  `openai/gpt-oss-20b` (current open-weight flagship with JSON mode). Bump
  `GROQ_MODEL` in `api/predict.ts` if Groq rotates the catalog again.
- **API route is dev/preview-only**: `/api/predict` is Vite middleware, so
  serving `dist/` from a static CDN alone will 404 that route. For a static
  deployment, move `handlePredictRoute` into a serverless function (Vercel
  `api/predict.ts`, Cloudflare Worker, etc.) — the handler is shaped for that.

## Extending the solution

The reducer boundary is the seam for turning the twin into a real one:

- **Real telemetry** — replace the random-walk arithmetic in `TICK` with a WebSocket/MQTT
  ingestion that dispatches the same `TICK`-shaped state updates; the UI, charts,
  thresholds, alerts and role model are untouched.
- **Persistence** — the current design is intentionally stateless (no
  persistence, per the brief). A later build could snapshot `SimState` to
  `localStorage`/IndexedDB, or replay it from a log for forensics.
- **Second station (Maitri)** — add another `ModuleId` set + a station selector;
  `State.g modules`/`moduleSnapshot` already carry sub-system health generically.
- **Multi-mode drills** — extend the `WhatIfPanel` action set with e.g.
  `SIMULATE_SEA_INTAKE_BLOCK`, `SIMULATE_FASTFUEL` the same way `GEN_FAIL` works.
- **More AI channels** — `api/predict.ts` already passes ambient/load/fuel/sea;
  extend `PredictInput` with more channels (wind, sun-hours, hatch temps) and
  the lab sliders grow with it. The prompt and schema are the only touchpoints.
- **Real telemetry to the model** — feed the Groq payload a live sensor ingest
  instead of the simulation channel values; the model, fallback and UI are
  unchanged.
- **Time/pace controls** — expose `TICK_MS` and `TICK_DT_DAYS` (already constants)
  as a "sim accelerator" so a long fuel-drain scenario can be demonstrated in
  minutes.

## Non-goals & limitations

Deliberately out of scope for this MVP (per the brief, and to keep it
recognisably a *demonstration*, not a claim):

- **No real NCPOR data** — all telemetry is simulated and UI-labelled as such.
- **No second station** (Maitri) — Bharati only.
- **No real satellite / IoT integration** — store-and-forward is simulated
  edge behaviour, not a real link.
- **No persistence** — state resets on refresh.
- **No database or auth** — a thin Vite middleware serves the single
  `POST /api/predict` route; everything else ships as a static SPA (`npm run
  build` + any static host, or `npm run preview`). AI output is advisory:
  it is a *prognosis driver for the demo*, not a certified control-system
  safety layer.
